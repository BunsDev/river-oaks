# Optional crime: operator playbook

This playbook covers #596–#599's optional authored-rival crime loop. New towns default to danger off and PvP false. Existing checkpoints preserve their saved policy; deploying a compatible build does not reset an already enabled town to peaceful. No production activation, production backup access or deployment is performed by this document or its local acceptance fixtures.

## Release decision

Use the [#599 checklist](acceptance/crime-release-599.md). Require exact candidate revision and source hashes, focused and full verification, hosted checks where applicable, recovery rehearsal, measured performance with unresolved breaches identified, and accessibility/device evidence appropriate to the audience. Record the decision maker, approved room, audience, schedule and stop conditions. A green local test or an HTTP health response is insufficient authorization to enable danger.

The current implementation supports melee only against the two authored rivals. Residents are protected. Player combat has no consent path and remains unavailable even if a legacy policy flag says PvP true. The owner form cannot enable it and saves PvP false. Do not introduce opt-in player combat until consent, moderation and abuse protection have independent acceptance.

## Peaceful rollout and controlled rehearsal

1. Pin the approved candidate and its dependency lockfiles. Recheck deployment configuration: the existing `api/server.js` Vercel function is in `iad1`, has a 300-second window, and uses the existing authenticated Redis gateway. Fixture identity routes must remain excluded from production; do not copy fixture environments into a deployment.
2. In the authorized room, sign in normally as the gameplay owner. Open People → World rules and inspect the server's time, mode, enabled zones and last change. For an existing town, explicitly select Emergency off if the authorized rollout requires peaceful operation; verify another connected client sees mode off, PvP false and no targeted officers or capture holds. This is an account operation requiring the room's separate authorization, not an instruction to run it automatically in production.
3. For a local controlled fixture only, use the existing two-browser runner: `RIVER_OAKS_SHARED_JOURNEY=world-rules-shared pnpm run test:shared development`, then `RIVER_OAKS_SHARED_JOURNEY=crime-shared pnpm run test:shared development`. These runners own synthetic accounts and servers and use the shared browser queue. They do not establish live authentication or production routing acceptance.
4. An authorized activation uses the existing owner form: choose Westcreek Lane and/or South service lane, choose a schedule or all hours, set shared time only if deliberately changing it, keep player combat unavailable, then Apply rules. Schedule ranges are half-open and may cross midnight: 18:00–06:00 permits 00:00 and stops at 06:00. The local lighting slider never grants combat permission.
5. Verify a peaceful observer is never targeted, a permitted rival hit produces one health/star change, officers remain globally capped at six, sight loss searches only the last-seen location, surrender captures once and the walking player visibly arrives on valid safe ground. Verify leaving danger cancels pursuit without forgiving existing stars. Finish the fixture rehearsal with Emergency off and verify both clients agree.

## Emergency disable and incident response

Select **Emergency off: stop all danger now** from the owner controls. It remains available while an ordinary Apply acknowledgement is delayed. It uses the existing authenticated `{type:'worldPolicy',action:'emergencyOff'}` command without revision, cooldown or ordinary command budget. Delivery still depends on a functioning authenticated connection and transport; this is not an out-of-band service kill switch.

After the server accepts off, verify the authoritative snapshot on another client: `worldPolicy.violence.mode` is `off`, PvP is false, every remaining officer is returning with a null target, and surrender/capture holds are empty. Officers return and despawn; off does not erase wanted stars or undo already committed damage/arrests. Subsequent attacks cannot cause new harm; a retried committed attack may return its original receipt without another mutation.

If the panel is unavailable, use the same command from an already authenticated owner client through the supported socket command path. Never paste session cookies, tickets or tokens into an issue or shell transcript. If transport or Redis is unavailable, do not claim off succeeded: restrict access using the separately authorized hosting incident procedure, restore service, send off and verify it from fresh clients before reopening the room.

Record UTC time, room and build revision, policy revision/last-change kind, connection/lease failure categories, affected operations, and sanitized test/monitoring evidence. Preserve the first failure and raw receipts. Keep reports and audit records private; release summaries should contain aggregate counts, never session credentials or private player data. Use People → Report disruption for in-world reporting. Reporting stays available while surrendered; moderators use the existing authenticated ban/revoke controls and durable audit.

## Compatible recovery and rollback

Refresh, 2026-10-28 (claude:river-oaks-3d): since #646 merged on 2026-10-25 (`15334aad`) the authoritative private checkpoint is version **17** (crime actions, participants, evades and the action sequence; police grabs and subdued players) and the Redis writer generations are **21** without the character store and **22** with it; the paragraph below records the version 16 state the playbook was written against. A version 16 town restores into a 17 writer with no pending actions, participants or grabs; a 17 section cannot ride in an older envelope, and a 19/20 writer is fenced from a 17 room. The same rules apply: never roll back to a pre-#646 binary against a version 17 room; prefer a forward fix or a reviewed 17-compatible build with danger off.

Refresh, 2026-10-30 (claude:river-oaks-3d): #708 (residents react) raises the checkpoint to version **18** (pending resident alarms are cleared on load, so a v18 section carries the reaction state) and the writer generations to **23** without the character store and **24** with it. A version 17 town restores into an 18 writer; a 21/22 writer is fenced from an 18 room. Never roll back below #708 against a version 18 room. #708 merged on 2026-10-30 as `f0d01729`, so `main` writes version 18 rooms (`WRITER_GENERATION` 23 in `server/redis-room.js` at `ccffc5c8`).

The authoritative private checkpoint is version **16**. Current Redis writer generations are **19** without the character store and **20** with it; browser protocol remains **3**. The writer generation is distinct from the checkpoint version. Older writers are fenced, and builds unable to read version16 cannot safely take over. Do not roll back to a pre-police binary against a version16 room, change generation numbers backward, delete the writer fence, hand-edit/checksum production checkpoints or change namespaces to hide an incompatible migration.

Prefer a forward fix or an already reviewed checkpoint 16-compatible build with danger off. Pin the last known compatible code, world package/geometry and dependency locks. Retain a provider-supported consistent backup/snapshot under the deployment's approved private recovery procedure, with restore point, versions and integrity digest. The room's checkpoint and public view are committed atomically with consumed commands and replies; restoring only a world checkpoint while retaining newer queues/replies or account/moderation records without a consistency plan can replay operations or discard unrelated progress.

Rehearse restoration into an isolated nonproduction namespace first. Validate the exact district revision, checkpoint envelope/checksum, unrelated state, account appearance and moderation/access records; connect two fixture clients, exercise retries, replace the writer during pursuit/capture, then verify exactly one damage/star/arrest transition and preserved off policy. Test a failed/corrupt/incompatible restore leaves existing state untouched. Keep the original backup and failed receipts unchanged. Promotion of a restored environment, acceptance of lost progress, account-state reconciliation and production writes require an explicit incident decision.

The #599 local tests and existing Redis lifecycle suite cover bounded functional recovery. They do not prove that a particular hosted backup is complete or restorable. A production recovery rehearsal needs its own provider/environment evidence and authorization.

## Monitoring and stop conditions

Observe the existing 200ms room tick and five snapshots/second target, command acknowledgement and snapshot gaps, missed ticks, memory trend, raw/compressed snapshot/checkpoint sizes, Redis latency and fenced commit failures. Track attack accepted/refused/replay counts, officer count (never above six), invalid zero-star targets, duplicate arrest effects, stalled holds, join/reconnect failures and report submission failures. Use aggregate counters and sanctioned diagnostics; do not add private identities to public telemetry.

Stop or keep danger disabled for duplicated harm/arrests, invalid spawn/collision, a failed off command, protected-player targeting, stuck surrender, inaccessible safety controls, data compatibility failure or a material unexplained performance breach. Record local short-window findings separately from hosted load, native packaging, physical-device performance and human keyboard/screen-reader acceptance. Never raise the 32-player cap or claim global readiness from the local crime audit.
