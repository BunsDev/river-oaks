# Release 0.2.1: signed and notarized macOS build

Task `release-0-2-1-signed`, branch `release/v0.2.1-20261015`, owner `claude:river-oaks-1b`.

## Decision

v0.2.0 was published on 2026-10-15 as an ad-hoc-signed build. Val then asked to proceed with the release, and chose:
- a new 0.2.1 release rather than re-signing 0.2.0 in place;
- signing as "Developer ID Application: Soul Protocol LLC (9LR8Z8UQ9X)";
- a `notarytool` keychain profile, `river-oaks-notary`, that Val stores. No agent reads key files or keychain secrets.

Earlier records tie two changes to the release that adds Developer ID signing, so both are in this one:
- cookie encryption (`desktop/fuses.js`, `docs/superpowers/plans/2026-10-12-server-hardening-followups.md` item 7);
- the hardened-runtime microphone entitlement (`docs/superpowers/plans/2026-10-13-shared-voice.md`).

**Certificate.** The keychain holds two distinct Soul Protocol LLC Developer ID Application certificates:
- `EE732DF3…`: valid 2026-03-05 to 2031-03-06, under the G2 intermediate. It is listed twice, because it is in two keychains.
- `AA757543…`: valid 2026-04-30 to 2027-02-01, under the G1 intermediate.

The release signs with `EE732DF3…`, which has the longer validity. A timestamped, notarized signature stays valid after either certificate expires.

## Checks before merge

- `node --test desktop/tests/sign.test.js`: 6/6. This includes real ad-hoc `codesign --options runtime` with the entitlements file. The readback finds the runtime flag and exactly the two keys. The release check refuses the result as "signed by an ad-hoc signature; no secure timestamp".
- **Cookie encryption** (scratch Electron 44.7.0 probe, Chromium's `--use-mock-keychain`, so no real Keychain item):
  - A cookie written with the fuse off read back after the fuse was flipped on.
  - The new cookie was stored as `v10` ciphertext with an empty plaintext value. AES-128-CBC with the mock-keychain key decrypted it.
  - A build with the fuse off, opening that store, returned no cookies and left the table empty. That is the documented rollback cost.

- `pnpm run test:desktop`: 76/76 (69 before this change, plus 6 signing and 1 fuse test).
- **Branch package.** `pnpm run desktop:package` and `desktop:package:check` passed: the fuse wire matches with cookie encryption on, and the ASAR holds exactly the allowed files.
- **Trial Developer ID signature** of the branch package (not notarized): `pnpm run desktop:sign --identity EE732DF3…`.
  - Authority chain: "Developer ID Application: Soul Protocol LLC (9LR8Z8UQ9X)", then Developer ID Certification Authority, then Apple Root CA.
  - Team 9LR8Z8UQ9X, hardened runtime, secure timestamp, and entitlements exactly allow-jit and audio-input.
  - The helpers: GPU and Renderer have allow-jit only. Plugin has Chromium's three entitlements. The plain helper has ours. Each has the runtime flag and the same team.
  - `spctl` reported "Unnotarized Developer ID", as expected before notarization.
  - `desktop:package:check` still passed after signing.
  - The first run failed because pnpm passes a literal `--` through to the script. The script now drops a leading `--`, and the docs use `pnpm run desktop:sign --identity …`.
- **Smoke launch** of the signed app, with a scratch `--user-data-dir`:
  - The main process stayed up for 25 s, with its renderer, GPU and utility helpers running and no errors in the log.
  - Before sign-in the app only checks `/auth/session` and shows the device-code dialog. So no cookie was written, and the real-Keychain cookie path is first exercised by a live sign-in.

- **`pnpm run verify` (core): passed.**

  - server 599, with 154 Redis cases skipped because no `REDIS_URL` was set (this change touches no server code);

  - The first run stopped at `scripts/tests/pnpm-policy.test.js`, because `desktop:sign` lacked its `predesktop:sign` enforce-pnpm guard. The guard was added.
