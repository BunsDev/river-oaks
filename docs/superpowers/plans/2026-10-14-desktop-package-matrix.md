## Assumptions rechecked against current source

- `verify.yml` uses `ubuntu-latest` only, with `actions/checkout@3d3c42e5…` (v7.0.1), `pnpm/action-setup@ea17c68d…` (v6.1.0), `actions/setup-node@949feb24…` (v7.1.0, Node 24, pnpm cache), `actions/cache@55cc8345…` (v6.1.0) and `actions/upload-artifact@cf430e03…` (v7.0.2). Browser jobs render on Linux with `xvfb-run -a` plus `LIBGL_ALWAYS_SOFTWARE=1`, `LP_NUM_THREADS=2`.
- `desktop/package.js` packages the host platform and arch into `dist/desktop/TypeSafe Place-<platform>-<arch>/`; the binary is `TypeSafe Place.app` on macOS, `TypeSafe Place.exe` on Windows and `TypeSafe Place` on Linux. It stages `DESKTOP_FILES` under `desktop/`, `DESKTOP_SHARED_FILES` at their repository paths, writes `desktop/world-design-pack.json` and a minimal `package.json`, packs them as an asar and flips `DESKTOP_FUSES` with `strictlyRequireAllFuses`.
- `desktop/e2e.js` launches the development Electron from the repository root (the packaged build has the inspector fuse off, so Playwright cannot attach to it). `--dev` starts its own Vite server on a free port with the acceptance fixture (`RIVER_OAKS_ACCEPTANCE_FIXTURE=1`, local dev auth, an in-process town on a free port, an offline `/v1` bridge), passes `--use-fake-device-for-media-stream`, and writes `data/reports/desktop-development.json` (or `RIVER_OAKS_DESKTOP_REPORT`) and `output/playwright/desktop-development*.png`.
- `@electron/fuses` exports `getCurrentFuseWire(pathToElectron)`; `@electron/asar` is only a transitive dependency of the packager, so the asar listing check parses the asar header directly.
- #370 (icon, Windows metadata, Linux executable name, Windows-aware host resolution) has no PR and has not merged. Windows and Linux failures caused by those gaps are recorded on #370, not patched here.

3. Linux e2e. The runner pipes core dumps to `systemd-coredump` (`core_pattern` `|/usr/lib/systemd/systemd-coredump %P %u %g %s %t 9223372036854775808 %h %d`, with the core limit hard-coded so `ulimit -c 0` does not apply to it); `fs.suid_dumpable` is 2. Diag run [38655947356](https://github.com/BunsDev/river-oaks/actions/runs/38655947356) reproduced the failure and read the journal: the game renderer (`--type=renderer`) took SIGTRAP at 23:46:12, `systemd-coredump` started at once and logged "dumped core" at 23:51:05 (core truncated, 183.4 MB compressed, 31.8 s of collector CPU), and `render-process-gone` arrived the same second. A minimal app's 1 GiB renderer, directly and under Playwright, dumped 3 MB in under 1.4 s (diag runs [38655685008](https://github.com/BunsDev/river-oaks/actions/runs/38655685008), 38655947356), so the size of the game renderer's address space is what makes the dump slow. The kernel keeps a dumping process, with its open IPC channel, alive until the dump completes, and Chromium learns of a renderer's death from that channel. The browser was not frozen: a snapshot 1 s after the crash shows the browser main thread idle in `poll` and the renderer (1.4 GB RSS) in `do_exit`. The earlier reading that `render-process-gone` came "at app close" was a misreading: the test's catch block awaits `failedPage.evaluate` on the crashed page, which Playwright only rejects when Chromium reports the crash, so the report printed after the dump finished. Diag run [38657104883](https://github.com/BunsDev/river-oaks/actions/runs/38657104883) ran the unchanged e2e twice on one runner: with `kernel.core_pattern=core` and `ulimit -c 0` the renderer was reported gone 133 ms after the FATAL line and all 13 checks passed (56 s); with the image's `systemd-coredump` the report took 292 s and the check failed. Fix: a Linux step sets `kernel.core_pattern=core` and the e2e step sets `ulimit -c 0`, so the runner writes no core. The 60 s recovery wait and the check are unchanged. Product note (recorded on #370, not changed here): a Linux desktop that pipes cores to `systemd-coredump` delays the app's automatic recovery from a real renderer crash in the same way.
