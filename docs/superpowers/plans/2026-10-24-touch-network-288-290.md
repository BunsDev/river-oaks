## Objective

On touch phones and unreliable networks, the play client never gets stuck:

1. A touch-hold journey covers move and look at once, a second finger joining and leaving, touchcancel/pointercancel/lostpointercapture mid-hold, the page hiding mid-hold and the chat keyboard opening mid-hold. Nothing keeps moving, nothing is selected by accident, and keyboard behaviour is unchanged.
2. The same journey runs in Playwright WebKit, or each CDP-only helper records why it cannot.
3. A network journey goes offline during travel, sitting and an office or desk command, then back online. The connection UI stays truthful, and each action ends completed, refused or unknown with no blind replay.
4. A layout pass at 390×844 and 375×667 (portrait and landscape), a command-to-touch-path map, and a physical iPhone/VoiceOver checklist for Val.

Out of scope: the graphics-recovery low-memory step-down floor and its shard entry, which `integrated-expansion-mvp-20261023` (#623) owns. Also out: native iOS (#286), merge, deploy and new hosted CI jobs.

## Increments

### 1. Look with a second finger (#288)

- **Cause.** `createPointerGesture().begin()` refused non-primary pointers. A finger that lands while a thumb holds a walk button is non-primary, so the look drag dropped it.
- **Fix.** `begin(event, {anyFinger:true})` takes a later touch finger when the gesture owns none. The `walking-ui.js` look handler passes it. Picking (`main.js`) still needs the primary contact.
- **Regression.** `pointer-gesture.test.js` "a look drag may take a later finger…": 9/10 before the fix, 10/10 after.

### 2. Push to talk on touch (#288)

- **Cause.** The mic buttons had only a click handler. In push-to-talk mode, holding "Hold to talk" did nothing, and lifting turned the microphone on and left it on.
- **Fix** (`voice-ui.js`). A main-button press transmits while held, and pointerup, pointercancel or lostpointercapture stops it. The click that follows never toggles. Keyboard and switch activation (detail 0) still toggle.
- **Regression.** `voice-ui.test.js` "push to talk on touch…": failed with no pointerdown handler; 5/5 after.

### 3. Offline admission (#290)

- **Cause.** Only the 8 s / 5-check staleness watchdog noticed a dead socket.
- **Fix** (`connection-policy.js`). When the browser reports offline, 750 ms of silence is a dead socket, with no quiet checks. Online behaviour is unchanged. A socket that keeps delivering stays. The existing 1 s watchdog already calls `stale()`, so `multiplayer-client.js` is unchanged.
- **Regression.** `connection-policy.test.js` "a page the browser reports offline…": failed on the missing export; 6/6 after.

### 4. No reload during an outage (#290)

- **Cause.** `checkAccess()` runs every 15 s, and its `catch` reloaded the page on any failure, including a fetch that never reached the server.
- **Fix** (`access-recheck.js`, `access-entry.js`). The fetch is wrapped so a rejection is marked `unanswered`. Only an unanswered check keeps the district. Every server answer still reloads into the gate: signed out, another account, not approved, an error, or an answer that is not JSON. An `online` listener rechecks as soon as the network returns.
- **Regression.** `access-recheck.test.js`: failed with the module missing; 1/1 after.
- **Review.** This is the WorkOS/waitlist gate. Val should review it; it is its own commit.

### 5. Desk outcome (#290)

- **Cause.** Any failed save read "Not saved".
- **Fix** (`office-desk-ui.js` request wrapper, `office-desk-model.js`). A failure with no HTTP status is marked `unconfirmed`, and the model reports it while the operation is outstanding. The status reads "Not confirmed · your draft is kept here", and the retry repeats the same `operationId`. Server refusals still read "Not saved".
- **Regression.** `office-desk-model.test.js` "a save whose answer was lost…": 10 pass and 1 fail before; 11/11 after.

### 6. Chat focus on a phone (#288)

- **Cause.** On screens up to 900 px, opening the chat dock fires its toggle handler, which clicked `#community-close` even when no conversation was open. `closeDialogue()` then focuses the scene while walking (`community-ui.js:536`). The Town chat command focuses the chat field and opens the dock; the toggle event follows and takes focus back to the scene. The next text typed walks the player instead: W, A, S, D are movement keys.
- **Found by.** touch-hold scenario 6 on the fixed tree: "chat receives the typed text" failed.
- **Fix** (`town-chat.js`). The first fix closed only an open conversation. The independent review found that this dropped a late-response fence: the close also bumps `selectionEpoch`, which cancels a person selection still in flight. The close now always runs, and with no conversation open, focus goes back where it was.
- **Regression.** `town-chat.test.js` (new) checks both the cancellation and the focus. It fails on main (focus left on the scene) and on the first fix (no cancellation); 1/1 on the final fix.

### 7. Mic buttons keep a held finger (#288)

- **Cause** (found by review). The walk pad sets `touch-action: none`, but the mic buttons set nothing. A push-to-talk hold could turn into a browser pan, which fires `pointercancel` and cuts the speaker off.
- **Fix** (`voice.css`). `touch-action: none; user-select: none` on both mic buttons, as `player-avatar.css` does for the drive pad.
- **Check.** touch-layout reads the computed `touch-action` of both mic buttons and ↑.

### 8. Journeys and WebKit

- **touch-hold.** A 390×844 phone, chat folded by a tap first. It covers a tap, walking plus looking, a second walk finger, touchcancel, page hide, capture loss, the Town chat command, three fingers lifted out of order, and a rotation mid-hold.
  - Capture loss: the finger slides 20 px along the held button, the page releases capture, and the finger slides back. The capture a walk button sets at pointerdown stays pending until the pointer's next event, and releasing a pending capture loses nothing (Pointer Events, "process pending pointer capture"), so the first slide makes it active. The journey first checks `gotpointercapture`, then `lostpointercapture`.
    - Two earlier versions released capture before any move, and no `lostpointercapture` was delivered: a 1 px slide afterwards (127910c6) and a 20 px one (6d356c6b). The product code was right; the journey released a capture that had never become active.
  - Town chat: Chromium makes no click from a second finger's tap while another contact is held. So the journey opens the command dialog with `?` and runs Town chat with Enter while the thumb holds ↑ (run at 127910c6: a tap on Commands timed out).
  - Chromium uses CDP touches.
  - WebKit holds with the real mouse, taps with real touch, and dispatches `pointercancel`, because the browser's own cancel cannot be triggered. Two- and three-contact cases are recorded in `metrics.notRun`: Playwright's WebKit `Touchscreen` has only `tap()`.
- **touch-layout.** 390×844 and 375×667, portrait and landscape.
  - It records whether chat hides the pad on load, then folds chat.
  - Checks: all six pad buttons show; nothing overflows sideways; controls are on screen, uncovered and at least 44 px; the panel scrolls and returns focus; a conversation's close returns focus.
  - The audit counts only rendered controls (`checkVisibility()`). Before that fix, buttons inside the closed **More** were reported as covered.
  - In landscape, the top-right stack (People, Play & rides, Commands) covers part of the walking console. That is printed as KNOWN; any other cover fails.
- **network-transitions.** Travel, sit, a desk save whose reply is lost, and a second drop while rejoining (the ticket request is held).
  - Checks: admission within 2 s, "not confirmed" wording, refusal while offline, nothing sent twice, no reload.
  - The gate's raw fetch text is printed as KNOWN, because its fix lies in `multiplayer-client.js`.
- **Waits.** No fixed sleeps. Waits are on state; the network journey polls Node-side proxy state at 20–100 ms steps.

## WebKit panel focus (03:22Z run at b939f1e6)

- touch-layout in WebKit failed "closing the panel keeps focus on its toggle" at all four sizes: focus was on BODY. The toggle's click handler moves no focus (`sidebar.js`; only the keyboard shortcut asks for it). In Chromium, focus lands on the toggle only because Chromium focuses a tapped button; WebKit, like Safari, does not. The first explanation here was that WebKit leaves focus where it was; that was wrong (below).
- The check now taps the toggle, as a phone user would, and asserts per engine. In Chromium, focus must land on the toggle, exactly as before. In both, focus must never be inside the closed panel. On an iPhone, VoiceOver's cursor is separate from DOM focus; the ten-minute pass checks that it returns to the button that opened the panel.
- 8b028d48 expected WebKit focus to stay where it was. The 06:00Z WebKit run (`final-288c-webkit.log`, kept) failed both portrait sizes: focus had been on the chat fold's `SUMMARY` and ended on `BODY`. Landscape passed only because focus was already on `BODY`. The host slept from 05:03Z to 09:05Z, with brief dark wakes (`pmset -g log`, reported by the lander session), so that run is not clean evidence. The awake 03:22Z run at b939f1e6 also ended on `BODY` at all four sizes. Chromium runs the same handler code and keeps the toggle focused. So the likely cause is the engine: a WebKit tap on a button that doesn't take focus clears focus to the page. That is tested by an awake WebKit run on the corrected tree before it is committed. The check now expects the toggle in Chromium and `BODY` in WebKit. After a tap close, focus is therefore on the page in WebKit and on the toggle in Chromium. Movement keys listen on the scene (`#canvas-host`, `walking-ui.js:223`), so in either engine they wait until the scene has focus again. That is unchanged from main and listed under Decisions for Val. The keyboard path (`{ focus: true }`) returns focus to the scene, also unchanged.
