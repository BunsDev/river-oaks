## Increment 1: content filter

**Design.** `server/content-filter.js` reads `config/content-filter.json` (`refuse`: words
and short phrases; `mask`: fields masked instead of refused). Text and terms are folded
the same way (case, accents, look-alike digits and symbols, Cyrillic and Greek
look-alikes), then matched on whole words only, so nothing inside a longer word matches;
spaced-out letters ("k i l l") and a run-together phrase ("killyourself") fold too.
`screen(field, text)` answers the text to store, masked where the policy says so, or
`{ ok: false, reason: 'filtered', message }`. A username is always refused, never masked.
`RIVER_OAKS_CONTENT_FILTER=off` turns it off; `RIVER_OAKS_CONTENT_FILTER_FILE` replaces
the list. A malformed or missing file throws at start, so a server meant to filter never
runs without one.

**Where it is applied.** At the same seams that already screen blocks: the chat command at
both gateways (`app.js`, `distributed-app.js`), before `screenCommand`, so the world is
untouched; `social-api.js` (`send`), `groups-api.js` (`create`, `send`), `events-api.js`
(`create`) and `profile-api.js` (`save`), each of which both servers call; and
`waitlist.js` `setUsername` in the file and Redis stores. The refusals are 400 with
`{ error, reason: 'filtered' }`, and `chat_filtered` over the socket; the client shows the
server's message. Both bootstraps (`town.js`, `redis-backend.js`) build the filter from the
environment once and pass it down; every constructor defaults to the built-in list.

**Default list.** Severe slurs and direct threats (30 entries). It is a starting point for
Decision 1 in `docs/app-review-292.md`, not a policy.

## Increment 2: moderation routing

**Design.** One shared intake, `submitReport` in `server/moderation-reports.js`, behind
the socket `report` command on both servers. The reported account may be connected, a
recent chat author (someone who has left), or an account with a username; an unknown id
is refused. The report gets a uuid `id`, `content` (`message.text` quoted, cleaned, 280
characters; the reported account's last 3 chat lines; together at most 1,200 bytes so the
hosted audit entry stays under 2 KB) and `respondBy` (`MODERATION_RESPONSE_HOURS` after
`at`, 24 by default). The town store and the Redis store save all three with the line
(`at` passed through so the line and the notice agree). After the save, the notice
(`{ type: 'report', id, at, reason, reporter, reported, content, respondBy }`) is posted
to `MODERATION_NOTIFY_URL` with `MODERATION_NOTIFY_TOKEN` as a bearer token
(`server/moderation-notify.js`): https only (loopback http for tests), 20 sends per ten
minutes, 5 s timeout, no redirects, never throws, logs by report id only; the reporter's
answer never waits on it. `POST /api/moderation/reports/close { id }` (moderators, CSRF)
records `{ at, by }` in `MODERATION_FILE` / `<prefix>:reports:closed`, audits
`report_closed`, and is a 404 for an id no saved report has. The list route adds `id`,
`content`, `respondBy` (older lines: 24 h after `at`), `overdue` and `closed`, open
reports first. The Settings panel shows the content as text, the response target or the
overdue or closed state, and a Close report button.
