## Phone fixture: windowed phase reports

`?phone-frame-windows=N&phone-frame-seconds=S` (1–60 windows of 1–20 s) makes the
fixture-only frame reporter take consecutive windows after the view is playable.
Each POST adds that window's summed render phases, discontinuities, effective
quality (mode, scale, AO) and draw counts. The server validates phase names and
bounds and keeps 80 reports. The default stays one 5-second window. Production
builds never include it. `node --test server/tests/phone-fixture.test.js` 8/8.

### Run 1 and run 2 (2026-10-20, Safari, phone on its charger, untouched)

URL: `/?phone-report=1&phone-errors=1&phone-frame-report=1&render-audit=1&phone-frame-windows=30&phone-frame-seconds=10`,
launched with `xcrun devicectl device process launch --terminate-existing --payload-url … com.apple.mobilesafari`.
Raw records (ignored): `.runtime/ios-fit/run1-gardens-normal-records.json`,
`.runtime/ios-fit/run2-records.json`.

- Load: playable (loading and gate hidden, 1,049 draws) by 25.7 s (run 1) and
  27.8 s (run 2), with assets still streaming (40/60 and 71/95). No app or console
  errors in the diagnostic summaries at 6, 18 and 25 s.
- Auto settles within 20 s of playable at scale 0.6 with AO off (its floor), about
  874 draws and 3.26 M triangles, Apple GPU, 440×796 CSS viewport.
- First ~30 s after settling: run 1 frames 42 ms median (last 80 frames of
  window 2), run 2 53–63 ms, with 26–40 ms of synchronous render-loop work.
- Then, about 60 s after the last launch in both runs, frames step to
  **81 ms median (12.4 fps)** and stay there: run 1 windows 3–19, 2,090 frames
  over 169 s, interval p50/p95/p99 81/92/97 ms; synchronous work p50/p95 26/28 ms
  (32% of the interval). Per-frame phase means: pipeline submission 18.7 ms,
  interactions 4.9, players 2.0, community 0.25, trees 0.25, everything else ≈0.
  Run 2 repeated the step at the same offset.
- Not thermal: run 2 started fast again on an already-warm phone. The step's
  cause is not established. It is a near-exact doubling while the synchronous
  work stays flat, consistent with the display dimming or lowering its refresh
  rate after a minute without a touch. Unconfirmed: Val did not answer the tap
  check. Run 2 stopped reporting at 04:57:31Z (socket closed), consistent with
  the phone locking.
- Instruments did not attach: `xctrace record --device 00008140-000675110A0B001C`
  timed out "waiting for device to boot" over the Wi-Fi pairing (the CoreDevice
  id `75F0…` is not an xctrace id). No GPU timing or memory footprint from this
  session; a USB connection is needed next time.

outside is #289 work with visual review.

### Prepared A/B: lean sun-shadow casters

A development-only audit switch, `__riverRenderAudit.shadowCasters('lean' | 'all')`,
turns sun shadows off for shop interiors (already under their roofs), the
parked bikes and the bird cams, and restores them. Production builds omit it
(checked: no `shadowCasters` in `dist/preview/assets`). The phone fixture's
`?phone-frame-ab=shadow-casters` alternates windows between `all` (even) and
`lean` (odd). Interleaving also cancels any time-based effect such as the
unexplained step.

- Local WebKit, same scene: lean switches 381 meshes; draws 874 → 687 (shadow
  pass 452 → 256; main pass unchanged at about 410). Receipts
  `draw-census-local.json` and `draw-census-local-lean.json`.

- Expected phone effect at about 21 µs per draw: roughly 4 ms less submission.
