## Reproducibility and evidence identity

The original `world-expansion-baseline.js` is a useful exploratory harness: it fixes camera/quality, creates a fresh authenticated fixture per viewport, waits for assets, rejects software rendering, samples one and two full local renderers, and checks reconnect identity/position. It records one ten-second window per workload. That cannot evaluate the documented median-of-three, thirty-second performance budget. Its 73.60 MB transfer measurement is Vite development traffic, not a production download baseline; phone dimensions on an M5 Max are not mobile hardware measurements. Its selected-file hashes do not capture every uncommitted dependency or prove source stability through the run.

It captures HEAD, tracked source patch and untracked source files under the report directory and checks their combined fingerprint after acquiring the browser lock and at completion. Post-run review extracted `baseline-580-source.js` and added HEAD itself to the fingerprint; a temporary Git repository regression proves that clean committed changes, dirty files and untracked inputs all change the identity while `.env` stays excluded. The recorded twelve-window run predates that extraction; its captured HEAD and current isolated checkout HEAD were independently confirmed identical. A changed input fails the run. `compareTimingBudgets(baseline, candidate)` in `preview/audit/baseline-580-protocol.js` compares the median p95 across three windows for each workload against the proposed 10% limit. It refuses incomplete windows, missing/nonfinite warmup, invalid/duplicate repetitions, changed sources, unmatched device/browser/camera/quality/viewport/renderer and missing samples. It also requires valid source identity fields and compares actual framebuffer dimensions, viewport, quality scale/mode/occlusion/tail-shedding and render-pipeline settings before and after every window. A faster result produced by reduced pixel count or disabled effects is incomparable; volatile observed FPS and resource counts are not rendering settings. It returns `incomplete`, `failed` or `passed`; its scope is timing only. A self-comparison validates report shape, not performance improvement or release readiness. Cross-revision comparisons still require matched workload and review of host load and retained screenshots.

## Explicit proposed performance budgets

The existing 10% timing/download and 20% reconnect deltas remain **proposed engineering budgets**, not documented owner approval. The table below makes each gate's sample, unit and missing evidence explicit. Newly proposed readiness/memory/absolute-frame limits are reviewable decisions, not retroactive claims that existing measurements passed them.

| Gate | Proposed numerical limit | Measurement protocol / present limit |
| --- | --- | --- |
| Warmed frame interval p95 | Candidate ≤ 1.10 × matched baseline | Median of three 30 s windows after ≥5 s warmup, separately for each one-/two-player workload; retain p50/p99/max and observed FPS |
| Synchronous CPU submission p95 | Candidate ≤ 1.10 × matched baseline | Same windows; excludes GPU completion time |
| Target desktop frame interval p95 | ≤16.7 ms | Proposed 60 Hz target; named physical target and quality settings require approval; do not substitute two same-host renderers |
| Target physical mobile frame interval p95 | ≤33.4 ms | Proposed 30 Hz floor; actual phone/browser/quality and thermal session required; viewport emulation cannot pass |
| District-only initial transfer | ≤1.10 × baseline encoded transfer bytes | Three fresh-cache production-build loads; median; include initial document and required resources through asset-ready; Vite development bytes cannot pass |
| Initial player readiness and asset readiness | Each ≤1.20 × matched baseline median | Three cold fixture joins, separate timestamps and asset errors; hosted/network target remains a separate measurement |
| Reconnect | ≤1.20 × matched baseline median; same identity; ≤0.5 m drift | Three induced reconnects per workload; old/new baseline harness each measures one per profile, so this gate is presently incomplete |
| JavaScript retained heap after 20 round trips | ≤1.10 × warmed pre-loop baseline | Matched post-settle, equivalent collection state; coarse `performance.memory` alone cannot pass; retained shared caches separately named |
| Renderer resources after 20 round trips | No increase over warmed plateau: Δ geometries = 0, Δ textures = 0 | Same settled camera/content, with approved immutable shared caches prewarmed and counted in both baseline/final values; counts are not GPU bytes |
| Evicted chunk lifecycle | 0 duplicate active IDs/events; 0 owned timers/listeners/handles remaining | Real load/unload/failure/reconnect loops; require ownership instrumentation and explicit allowed shared resources |
| Errors and integrity | 0 asset failures/page errors; no identity loss, reload, unauthorized movement or changed District content | Required in every accepted sample/journey; a failed required check prevents acceptance |

Neither stability nor a relative regression budget guarantees enough absolute performance. Approval must select target devices and quality settings and ratify or change the proposed absolute frame/readiness/memory limits. GPU memory has no measured byte baseline or approved cap here; record it as an outstanding device-specific decision, not “stable” based on texture counts. Review raw sample variation and host load before treating any candidate/baseline pair as matched. Twenty-loop streaming, content-load recovery and actual shared-session scalability belong to the active #582/#583/#587 owners and are not proved by this stationary baseline.
